# Rule Creator

プロジェクトルールを作成・編集するスキル。`skill-creator` のルール版にあたる。

ルールは「エージェントがこのリポジトリで作業するときに守るべき約束事」を Markdown で書いたもの。常時読み込まれる指示と違い、**特定のファイル種別やディレクトリに閉じた指示**を必要なときだけ効かせられるのが利点。

## 置き場所は実行環境で変わる

| | 常時読み込まれる規約 | 個別のルール |
|---|---|---|
| Claude Code | `CLAUDE.md` | `.claude/rules/*.md`（サブディレクトリも再帰的に読まれる） |
| Codex | `~/.codex/AGENTS.md` | リポジトリまたは各ディレクトリの `AGENTS.md` |

**どちらか分からなければユーザーに尋ねる。** 置き場所が決まらないと、ファイル名もスコープの書き方も決まらない。

`.claude/rules/` の仕様は https://code.claude.com/docs/en/memory の "Organize rules with `.claude/rules/`" 節を参照する。

## いつ使うか

- 会話の中で「今後はこうする」と決めた方針を恒久化したいとき
- 特定のファイル（例: `*.test.ts`、`src/api/**`）にだけ効かせたい規約があるとき
- 常時読み込まれる規約ファイルが肥大化してきて、トピック別・パス別に切り出したいとき

逐次手順や「呼び出したときだけ動く」ワークフローは**ルールではなくスキル**（`skill-creator`）が適切。常に全セッションで必要な普遍的な指示は、常時読み込まれる規約ファイルの方が適切。迷ったら下表で判断する。

| 永続化したいもの | 置き場所 |
|---|---|
| 全セッションで常に効く普遍ルール | 常時読み込まれる規約ファイル |
| トピック別・パス別の規約 | 個別のルールファイル（このスキルの対象） |
| 呼び出し時だけ実行する手順 | スキル（`skills/<name>/SKILL.md`） |
| 機械的に強制したい禁止事項 | フック（対応している環境のみ） |

## 手順

### 1. 意図を捉える

ユーザー（または直近の会話）から次を引き出す。会話に既に答えがあるなら、推測で埋めず確認を取る。

1. **何の規約か** — どんな振る舞い・書き方を統一したいか
2. **なぜ必要か** — 背景・理由（ルール本文に「理由」として残す価値があるか判断する）
3. **対象範囲** — 全ファイルか、特定のファイル種別／ディレクトリか
4. **既存ルールとの関係** — 既存ファイルへの追記か、新規ファイルか。矛盾する規約がないか

### 2. スコープとファイルを決める

- 既存のルールを `ls` で確認し、同テーマのファイルがあれば**追記**を優先する（規約の分散を防ぐ）
- 新規なら内容が分かるファイル名にする（例: `test.md`、`naming.md`、`api.md`）
- スコープを絞るなら、リポジトリの実ファイルを `Glob` で確認して **過不足のない範囲** を決める
  - 例: 「TS のテストファイル」なら実在拡張子を確認する（`.test.ts` だけか `.test.tsx` もあるか）
- スコープは `paths:` フロントマターで書く。`.claude/rules/` では実際にフィルタとして効き、`AGENTS.md` では機械的には効かないが、**書いてあればエージェントは適用範囲として読む**ので書き方は変えなくてよい
  - ディレクトリ単位で閉じる規約なら、そのディレクトリに置く方が確実（`AGENTS.md` はこれが本来の絞り方）

### 3. ルールを書く

- 見出しは `# 〇〇規約`
- 箇条書きで簡潔に。**why（なぜそうするか）を書く**。what はコードから読めるので冗長に書かない
- 重要な規約は理由・代替案をネストして添える
- 文体は**日本語かつ適度な敬語**（プロジェクトの開発ルールに準拠）
- 1ファイルが長くなりすぎないようにする（肥大化したらトピックで分割）

過度な `MUST`／`NEVER` の羅列は避け、理由を説明してエージェントが納得して従える形にする。

### 4. 検証する

- `paths:` が正しい YAML 配列になっているか。スコープ不要なら**キーごと付けない**
- glob が対象ファイルに実際にマッチするか `Glob` で確認する
- 既存ルール・常時読み込まれる規約ファイルと矛盾しないか見直す
- 書いたファイルパスをユーザーに伝え、必要なら commit/push する（このリポジトリでは作業ブランチへ）

## 例

会話で「分岐や関数が増えない範囲でテーブル駆動テストにしたい」と決まり、TS テストファイルに限定するケース。**書き方は環境によらず同じで、置き場所だけが変わる。**

```markdown
---
paths:
  - "**/*.test.ts"
---

# テスト規約

- 分岐や関数が増えない範囲で、なるべくテーブル駆動テスト（`it.each` 等）にする
  - 理由: 同種のケースを表形式で一覧でき、ケース追加が容易で網羅性を読み取りやすい
  - 注意: テーブル化のために条件分岐やケースごとのコールバック関数が増えるなら、可読性を優先して個別のテストに分ける
```

## やってはいけないこと

- 逐次手順や「実行する作業」をルールに書く（それはスキルの領分）
- 対象を確認せずに当て推量の glob を書く
- 既存ルールと重複・矛盾する規約を別ファイルに増やす
- why を書かず what だけを並べる、あるいは理由なき MUST を羅列する
- 実行環境を確かめずに置き場所を決める（`.claude/rules/` に書いても Codex は読まない、その逆も同じ）
- `AGENTS.md` に書くとき `paths:` を消してしまう（機械的には効かないが、適用範囲を伝える情報として残す）
