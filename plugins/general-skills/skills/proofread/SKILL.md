# Proofread

日本語のテキストを、5つの観点に分けてレビューし、優先度順に報告してから直すスキル。

校正は「読めば分かる」作業に見えて、実際には**種類の違う注意力を同時に要求される**。誤字を探す目で事実確認はできないし、係り受けを追っている最中に表記揺れは目に入らない。観点ごとに独立した読み手へ分けるのはそのため。1人で通し読みするより漏れが減る。

## 全体の流れ

```
0. 下調べ  →  1. 観点別レビュー  →  2. 報告  →  3. 修正  →  4. 仕上げ
```

### 対象の大きさに合わせる

この手順は**数千字以上のまとまった原稿**を想定している。記事、書籍の一章、登壇資料、長めのドキュメント。

短いテキスト——PR の説明文、リリースノート1本、README の数段落——のために観点を5つに割るのは割に合わない。段取りのコストのほうが読む手間より大きい。**その場で通して読み、気づいたことを重要度順に伝えれば足りる。** 判断が要るものだけ確認を取る、という後半の考え方は規模によらず使える。

境目は字数ではなく、**一度読んで全部を頭に入れておけるか**。入るなら分けなくていい。

## 実行環境による違い

- **観点の回し方**: サブエージェントを並列起動できる環境なら5観点を同時に走らせる。できなければ観点ごとに順番に回す。**逐次でも観点は混ぜない** —— 指摘はメモに溜め、全観点が終わるまで1文字も編集しない
- **選択肢の提示**: 選択肢 UI がある環境ならそれを使い、修正後の文そのものを選択肢に入れる。無ければテキストで番号を振って同じものを出す
- **規約の読み取り**: プロジェクトの規約ファイル（`CLAUDE.md` / `.claude/rules/*.md` / `AGENTS.md` など、その環境が読むもの）から文体・表記の指定を拾う

## ステップ0: 下調べ（レビューを始める前に必ず）

**このステップを飛ばすと手戻りが出る。** 表記をどちらに統一するかユーザーに確認したあとで、プロジェクトに既定の答えがあったと分かると、確認済みの判断がひっくり返る。**すでに決まっていることは聞かずに従う**のが、相手の時間を使わない。

対象ファイルを Read したうえで、次を確認する。

**明文化された規約**
- プロジェクトのエージェント向け規約ファイルに文体・表記の指定がないか
- スタイルガイドや執筆要項が同梱されていないか

**周辺のテキストとの整合**
- 同じディレクトリの他の原稿を数本読む。書籍・連載・シリーズものなら、**表記は全体で揃っているべき**で、その原稿単独の多数決では決められない
- 「この原稿だけひらがなが多い」のか「プロジェクト全体がそうなのか」は、隣を見ないと判断できない

**編集してはいけない場所**
- 冒頭に `<!-- Generated from ... -->` のような注記がないか。**自動生成部分を直接編集しても次の生成で消える**ので、生成元のファイルを直す
- 引用ブロック、コードブロック、外部から転載した文章

ここで分かったことは、後のステップで判断材料になる。「このプロジェクトでは全角と半角の間にスペースを入れる」と分かっていれば、ユーザーに聞くまでもない。

## ステップ1: 5観点のレビュー

5つの観点を**互いに独立した読み手として**回す。並列に起動できる環境なら同時に、できないなら観点ごとに順番に。いずれにせよ、**1つの観点を見ている間は他の観点を気にしない**のが要点で、まとめて1回読むのとは結果が変わる。

各観点で共通に守ること:

- **ファイルを編集しない。** 指摘だけを返す。並列で同じファイルを書き換えたら壊れるし、逐次でも後の観点が前の修正結果を見ることになって指摘がぶれる
- 出力は `行番号 | 該当箇所（原文引用） | 問題 | 修正案` の形式で、重要度（高/中/低）を付ける
- **実際に本文に存在する記述だけを指摘する。** 憶測で「こう書いてあるはず」と書かない
- 裏取りできなかったものは「未確認」と明記する。断定しない
- ステップ0で分かったプロジェクトの表記ルールを前提に置く

### 観点1: 誤字・脱字

漢字の変換ミス（同音異義語）、文字の抜け・重複、句読点の抜け、**文末の句点漏れ**、送り仮名の誤り。

### 観点2: 表記の統一

全角／半角の混在、ひらがなと漢字の使い分け（「時」と「とき」、「事」と「こと」、「言える」と「いえる」）、同一語の表記揺れ、数字表記、箇条書き記号や見出しレベルの一貫性。

**同ディレクトリの他ファイルとも突き合わせる。** 単体では統一されていても、書籍やシリーズの中で浮いていることがある。

### 観点3: 文法と構造

主語と述語のねじれ、ら抜き・い抜き・さ入れ、敬体と常体の混在、一文の長さ、係り受けの曖昧さ、助詞の誤り、段落構成。

主述のねじれは書いた本人には見えにくく、指摘されても「どこが変なのか分からない」となりやすい。**どの語とどの語が噛み合っていないかを名指しする**と、後の説明が楽になる。

### 観点4: 数字・固有名詞

日付、金額、人名、地名、商品名、作品名、イベント名、バージョン番号。**Web 検索・取得で一次情報（公式サイト・公式ドキュメント）に当たる。**

引用ブロックがあれば、引用元の原文と一字一句照合する。引用は改変してはいけないので、**原文が全角数字や半角クォートでも、そのままが正しい**。校正で「揃える」対象からは外す。

### 観点5: 事実確認

本文内での矛盾（時系列、経歴、数値）、内容の事実誤認、**出典のない権威づけ**（「研究で示されている」「一般に言われている」）、断定が強すぎて反論を招く主張、**執筆メモの残骸**（`(あとで書く)` `TODO` `引用つけたい` など）、引用の出典が参考文献にあるか。

手順書や技術記事なら、**書かれたとおりにやって読者が再現できるか**も見る。著者の環境では動いているので、前提のインストール、初期化の一手順、呼び出し忘れといった抜けは本人には見えない。「この説明だけで動くか」を一度なぞってみると出てくる。

## ステップ2: 優先度順に報告

5観点の結果が揃ってから、重複を排してまとめる。**複数の観点から独立に挙がった指摘は信頼度が高い。**

報告の順序は、直さないと困る度合いで決める。

1. **公開事故になるもの** — 執筆メモの残骸、句点漏れ、壊れたリンク、引用記号の欠落
2. **要・本人確認** — 裏取りできなかった事実
3. **構成上の問題** — 伏線の未回収、タイトルと中身の食い違い、自己矛盾、出典なき権威づけ
4. **文法** — 主述のねじれ、い抜き、助詞
5. **表記** — 表記揺れ、スペース、記号

### 指摘どうしのつながりを見る

一覧に並べる前に、**同じ原因から出ている指摘がないか**を見る。

「速度が最速だと断定している」と「ベンチマーク結果を貼るメモが空のまま」は、別々の指摘に見えて同じ穴の裏表になっている。片方だけ直すともう片方と噛み合わなくなるので、**まとめて提示して一度に判断してもらう**。

章をまたいだ矛盾も同様に、片方だけ直すと壊れる。

### 「確認できなかった」と「間違っている」は違う

著者の実体験は Web に情報がないことが普通にある。登壇歴、社内の役割、コミュニティでの活動、参加したイベント。**検索で出てこないことは、存在しない証拠にならない。**

「公開情報では確認できませんでした。正式名称をご確認ください」と伝える。「そのイベントは存在しません」と書かない。著者の方が事実を知っている。

**問題がなかった項目も報告する。** 「放送期間・話数・引用5箇所は一次情報と一致していました」と書けば、著者はその部分をもう見直さなくて済む。

## ステップ3: 修正

**2段階に分ける。** 全部まとめて聞くと判断が雑になり、全部まとめて直すと意図しない改変が混ざる。

### A. 判断の要らないものは一括で適用

- 明らかな誤り — 句点漏れ、い抜き、助詞の誤り、敬体への常体混入、送り仮名
- プロジェクトのルールで正解が決まっている表記（ステップ0で確認済みのもの）
- 箇条書きと見出しの文言の不一致など、片方に揃えるしかないもの

適用したら一覧で報告する。

### B. 判断が要るものは1件ずつ

表記をどちらに寄せるか、断定をゆるめるか、構成に手を入れるか。これらは著者の意図次第なので、**1件ずつ承認を取る。**

各件について:

1. **現状の文を引用する** — どこの話か迷わせない
2. **どこが問題かを説明する** — 「主述のねじれ」と名前を言うだけでは伝わらない。**どの語とどの語が噛み合っていないか**、そのままだと**どう読めてしまうか**を書く
3. **選択肢の形で提示する** — 選択肢には**修正後の文そのもの**を入れる。説明を読まなくても、見比べれば選べる
4. 承認されたら修正し、次へ進む

選択肢には「修正しない」を必ず含める。著者の文体としてあえてそう書いていることがある。

### 何件を、どの順で聞くか

**判断を仰ぐ数は絞る。** 確認事項を10件並べると、相手は3件目で疲れて残りを流し読みする。それでは1件ずつにした意味がない。

- **公開事故と事実に関わるものを先に。** 表記の好みは最後
- **ステップ0で前例が分かっているものは聞かない。** プロジェクトの既定に従う
- 低優先の表記揺れは、1件ずつ聞かずに**まとめて一度に確認する**
- 件数が多いときは「まず重要な3件を確認させてください」と区切ってよい。残りは後から片付く

判断が要るかどうかは、**間違えたときに誰が困るか**で決まる。誤字は直せば済むが、主張を弱めたり内容を補ったりすると、著者が言いたかったことが変わる。後者だけ聞けばいい。

**説明の例**

> **現状の文**
> > 最初の**出会いは**ラッシュデュエルを生み出すための戦いでしたが、主人公たちの前に立ち塞がるように**現れ続けます**。
>
> 文頭の主語は「**出会いは**」ですが、後半の「**現れ続けます**」の主語はオーティスです。つなげて読むと「**出会いが現れ続ける**」ことになってしまいます。
>
> 「〜が」は前後で同じ主語について語るときに使う接続助詞なので、主語が変わるここでは文を分けるか、後半の主語を明示する必要があります。

### 修正案を作るときに踏み外しやすいところ

**内容の解釈を勝手に足さない。** 直すのは文の構造であって、書かれていないことを補うのではない。

作品や技術の内容に踏み込んだ要約を修正案に混ぜると、事実誤認を作り込むことがある。原作を読み、その技術を使っているのは著者の方で、こちらは原稿から読み取れることしか知らない。**「たぶんこういう意味だろう」と補った内容は、著者に確認するか、修正案から外す。**

断定を主観に寄せる修正（「〜です」→「〜と感じています」）は有効だが、**主張そのものは変えない**。著者が言いたいことを弱めるのではなく、反論の余地がある部分を「これは私の見方です」と正直にするだけ。

出典のない権威づけは、著者が実際にその文献を読んだかどうかで対応が変わる。**読んでいないなら出典を付けてはいけない。** 「あくまで私の実感ですが」と書けば誠実で、指摘もされない。

## ステップ4: 仕上げ

- 適用した変更を分類して一覧で報告する。「何をどう直したか」が一覧で見えると、著者はそれ自体をレビューできる
- 生成元ファイルを直した場合は、**生成コマンドの実行を促す**。生成物に反映されるまで変更は見えない
- **未着手のまま残した指摘があれば、必ず明示する。** 「あとはご判断ください」で終わらせず、何が残っているかを列挙する

シリーズものの一本を校正したなら、**そこで決まった表記の方針を書き残すことを提案する**。「今回は全角と半角の間にスペースを入れる、長音符は付ける、補助動詞はひらがな、で揃えました。プロジェクトの規約ファイルか執筆要項に残しておくと次の章から迷いません」——同じ判断を毎回やり直さずに済む。

プロジェクトに校正ツールが整備されているなら、実行を勧める。ただしツールが拾えるのは機械的に判定できる範囲だけで、主述のねじれや事実の誤りは検出されない。**ツールが通ったことは、校正が終わった証拠にはならない。**

このスキルが行うのは、テキストの読み取りと編集、それに裏取りのための Web 検索・取得（観点4で使う）までで、**シェルは実行しない**。コマンドを走らせる必要がある場面では、何を実行すべきかを伝えて著者に委ねる。

## やってはいけないこと

- 観点別レビューの担当にファイルを編集させる（書き換えが混ざって壊れる）
- 検索で出てこない固有名詞を「存在しない」と断定する
- 引用ブロックの中を「表記統一」の名目で書き換える
- 判断が要る修正を、承認なしでまとめて適用する
- 原稿から読み取れない内容を補って修正案にする
- 指摘だけ並べて、何が問題なかったかを伝えない
